# Validate-course: cases read by part

The cases of `tasks/validate-course.md` (session mode) that only some checks meet. Read only the part that applies,
from its heading to the next one; `node specs/dashboard/status.mjs` shows the track and the unit's state.

## Design track

Applies on `__Track:__` `design`.

The unit's file is its recorded path in the Material cell of `## Sessions` (never the File Structure mode), and the whole file is the unit — every `check-material` finding is in scope. It checks only what the design track changes: syntax (`tasks/validate-syntax.md`), the header (the theme of `## Visual Identity`, no second theme on top, template imports kept), images (path, alt text, credit, licence and the checklist's image items — `node specs/dashboard/read-source.mjs <file>` lists them; an `existing` entry counts as placed, a kept unclear licence carries `terms.licenseUnclearKept` in the entry and in the credits) and contrast (`check-material.mjs`: each `contrast {ratio}:1 < {need}:1` error is a `[mechanical]` ❌). Step 4b fixes only the header, image lines, alt texts and the credits chapter; a contrast finding is fixed in `## Visual Identity` and written into every file by `:apply-theme`, never in one header (that file would lose the theme, and `:apply-theme` would bring the old colour back). **Only these four design checks apply; every other item is a content hint:** learning objectives, duration, Type and Method, persona and style, templates, `reference-checker`, facts, and the content-like `check-material` findings (answer patterns, options that give the answer away) — not judged, and those report fields say "not checked – design track" (translated); `result_rules` count only the design checks, and `Unit entry (journal)` covers only the lines the design track owns (image block, report, decisions). A content observation never makes the check FAIL, never gives PASS with concerns and never stands under "Still missing": it is a hint ("Note: …") in the report, and the overview gets one `decide` item `content-hints-{n}` with `source: {check: n}`, its `href` on the report heading, `how` one line per hint (page title + one sentence) and the Teaching-Agent's `:quick-fix {n}` — as `layout-suggestions-{n}` (`tasks/review-images.md`). There is no learner review (`review-as-persona`) and no `:try-as-learner` offer: the content did not change. Done and approval as on every track (step 6, `data/quick-fix-cases.md` → Approval after a review). No separate course check runs: every unit done is the course check (computed; publishing waits for every unit), and `:validate-course` without a number runs this check for each unit not done. `### Latest Validation Summary`, which publishing reads (`tasks/create-project.md`), follows the unit reports without a new run (`Mode: course`, step 9 form): **design course result = PASS exactly when every unit is done (passed and approved), otherwise FAIL**; the course-level checks (a) of step 9 are skipped (Outline and Didactics wait). The write that makes the last unit done writes it, and so does every later write that changes a unit's report or approval; before that no unit check writes the summary, so no `Result: PASS` stands while a unit is not done.

## PASS with concerns

Applies when the unit's report says PASS with concerns (step 0), or when this check ends with it (step 8).

**Concerns only:** if the unit's current report says PASS with concerns and nothing changed since it (no material change, no entry in its "Changed after the check" block newer than the report), do not check again: say so in one line and go straight to the concerns (step 8, "With **PASS with concerns**"), then rewrite the report's outcome, status line and overview. A new full check runs only after a change.

With **PASS with concerns**: go through the concerns one at a time, as at the Publishing Gate — fix it now (`:quick-fix`, or `:coauthor-materials {number}`) or accept it as is with a short reason — for this unit (a dated entry in the session's decisions list) or, if the same concern applies to every unit, for the whole course (one `:save-decision`); listed in the save summary. A concern whose acceptance would contradict `## Course Context` (e.g. a special need of the target group, such as read-aloud for a learner with dyslexia) is named as such and needs its own explicit confirmation. Then, if something was fixed, the short re-check of the changed area (`tasks/quick-fix.md` → Change path) inside this run: its dated line ends with "· re-checked: {how}" (`terms.recheckDone`, translated) and the outcome line gets no "short re-check open" — the check is complete; if every concern was accepted, the outcome becomes PASS without a new check. When called from `:build-session`, do not ask — return the result to the caller, whose loop decides.

**A concern that waits for the instructor** ("I'll decide once I've looked at it on the tablet", translated) is no decision yet: keep it under the report's open items as `- ⏸ {concern} – {what the instructor will do first}` and add the look as a preparation item. When the instructor comes back to it, remove the ⏸ and decide it as above. Only the check result words come from this task: another assistant never announces them ("it will then say 'passed – …'"), and only a check names the unit's check time.

## Only own photos left

Applies when the result is PASS and the only ⏳ items are pictures the instructor supplies (step 7).

The approval does not wait for them. After the result, ask once in a form "Do you approve {unit} {n} – your photo can follow later?" (translated) with "Approve", "Look at it first" (👁 the learners' view) and "Later". "Approve" records `- **{date}:** material approved` (translated) in the session's decisions list — one write, then `write-dashboard`.
